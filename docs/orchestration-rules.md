# 总控与执行线程协作规则

## 1. 适用边界

本规则用于总控线程拆解、派发和验收由多个执行线程（子 agent）协作完成的任务；单线程即可完成的小任务不强制走本流程

删除影响：多线程协作时职责不清，范围、进度和完成判据只存在于对话上下文

## 2. 总控线程职责

- 定界与分解：把目标拆成可验证的执行单，固化书籍、索引组、章节范围、筛选条件、任务数和输出目录
- 派发与交接：向执行线程提供目标、已知结论、精确路径和规则约束，不让执行线程重复探索
- 规则守门：执行 SQLite 与备份、L2 按书籍和索引组隔离、密钥不出环境变量、书籍目录收口等规则，冲突时按 Agent.md 优先级链裁决
- 台账管理：维护任务状态、成功项、失败项和断点，已成功且产物有效的项目不重跑
- 验收闭环：按完成判据逐项核验证据，不凭 Prompt、日志或任务启动状态推定完成
- 文档同步：书籍阶段变化回写书籍 README，规则和入口变化回写 Agent.md 与 docs/
- 线程收口：执行线程返回后核对文件、数量、日志和读回证据，将验收结论写回项目文件，不把执行线程的口头完成声明直接当作项目状态

删除影响：执行线程各自为战，范围漂移、重复消耗和进度误报无人拦截

## 3. 执行线程职责

- 只按执行单范围工作，不扩大批次、不改无关文件
- 复用交接中给出的路径与结论，不重复全仓探索
- 产出可核验证据：文件落盘清单、数量校验、写入读回结果
- 中断或失败时保留断点和失败原因，只重跑失败项
- 向总控交接时说明实际修改文件、验证命令、结果证据和剩余风险，不在项目文件之外维护另一套状态

删除影响：执行结果无法验收，中断后无法续跑

## 4. 执行单要素

每张执行单必须写明：目标、书籍、索引组、章节范围、筛选条件、任务数、输出目录、完成判据和验证方式，与数据与批量任务规则第 5 条一致

非简单 Task 开始前，总控必须按 [`docs/task-control-card.md`](task-control-card.md) 建立任务控制卡，至少锁定目标、本期包含与不包含、输入输出契约、已确认决策、停止条件、所需审查关、完成证据和当前授权边界

控制卡是当前 Task 的执行摘要，不替代设计基线和实施计划；三者冲突时先暂停，由总控核对上游信源后更新控制卡

删除影响：可能把子集误当全量，或向错误对象批量写入

## 5. 沟通标签与裁决语义

总控、执行线程和审查线程的关键结论统一使用以下标签：

- `DECISION`：已确认且对当前或后续执行生效的决策，必须同步到对应项目信源
- `BLOCKER`：不解决就不得进入下一关的已确认规格缺口、明显缺陷或安全问题
- `FOLLOW_UP`：合理但不阻断当前 Task 的增强、新需求或长尾案例，只记录后续清单
- `QUESTION`：尚未裁决且不能从当前信源唯一确定的问题，在裁决前不得擅自实现

执行进展、普通说明和无需裁决的信息不强制加标签，避免把所有沟通变成形式化记录

`DECISION` 未回写项目文件前不得作为跨线程持久信源，`QUESTION` 不得在实现或测试中被隐式固化为规格

删除影响：建议、阻断项和未决问题会混在一起，执行者可能把后续想法当成当前需求

## 6. 状态记录约定（文档唯一信源）

- 书籍当前阶段与下一步写在 `books/<book_id>-<book_name>/README.md`，阶段变化即更新，统计数字注明统计日期
- 批量执行过程落在书籍 `runs/YYYY-MM-DD-<task>-rNN/` 批次目录，含输入、日志、结果和断点
- 规则与入口以 `Agent.md` 和 `docs/` 中的当前设计基线为准；`docs/superpowers/plans/` 保存可执行实施计划，是否生效由对应设计基线、计划状态和总控台账共同确认
- `docs/superpowers/specs/` 保存设计、审查 Brief 和执行记录，`docs/superpowers/evaluations/` 保存专项评估材料；两者默认作支持证据，不自动成为当前执行规格
- 已完成或已被替代的计划保留作历史证据，不得覆盖当前设计基线；目录位置和文件日期不单独决定优先级
- 线程上下文中形成的结论必须沉淀为文档后才算数，新线程只读文档即可接续

删除影响：进度和决策只留在对话里，新线程无法接续，旧结论被误当现状

## 7. 不可逆设计审查关

出现以下任一情况时，总控必须在编码或写入真实数据前完成不可逆设计审查：

- 新增或修改数据库主键、唯一约束、外键、级联删除或历史快照语义
- 导入、迁移、覆盖、删除、批量改写或无法自动回滚的持久化操作
- 新增或修改对外 API、跨任务数据契约、稳定 ID 规则或幂等语义
- 实现选择会让后续阶段必然发生数据迁移、全量重建或对外契约重写

审查输出必须包含：不变量、对象身份与版本的区分、历史数据保留方式、重试与幂等语义、删除与失败影响、迁移和回滚路径、替代方案与选择理由

只有所有 `BLOCKER` 已解决、未决产品选择已标记为 `QUESTION` 并由有决策权的角色裁决、回滚或重建方式可验证时，总控才能放行实施

删除影响：数据模型和公开契约问题会在实现后才暴露，造成迁移、兼容和历史数据修复成本

## 8. 复杂度哨兵与审查裁决

审查意见由总控按以下四类归档：

1. 已确认规格缺口：当前实现遗漏或违反仓库文件中已经确认的要求，可以阻断
2. 明显代码缺陷：数据错误、非确定性、契约不一致、安全问题或测试失败，可以阻断
3. 新产品需求：超出当前规格的新能力，只记录后续建议，不阻断
4. 开放式长尾表达：新的语言变体、边缘样例或无法穷举的自然语言覆盖，只记录后续建议，不阻断

审查者不得用无限自然语言反例隐式扩写规格，发现超范围案例时标记 `FOLLOW_UP`，不得返回 `CHANGES_REQUIRED`

质量审查发现结构性风险时优先建议简化实现、收紧输入契约或调整层级职责，不优先要求增加条件、正则和变体测试

出现以下任一情况时触发复杂度哨兵：

- 同一任务进入第 4 次修复，即已发生 3 次修复循环
- 实际代码或测试规模明显超过计划预期
- 连续提交只增加表达变体、关键词或正则兼容
- 当前实现开始依赖后续任务尚未锁定的字段或契约
- 修复一个样例持续破坏另一个已通过样例

哨兵触发后总控必须暂停新派发，确认共享文件没有并发写入，重新读取规格信源，列出保留、删除、下沉和延期项，压缩实现并锁定任务间契约

压缩后只允许一次最终规格审查和一次最终质量审查，审查边界、允许阻断的类别和后续建议格式必须在执行单中写明

总控对审查分类和是否阻断拥有最终裁决职责，不能把范围判断完全交给审查线程

删除影响：审查会不断生成隐含规格，执行线程持续追加规则，任务无法形成稳定接口和完成状态

## 9. 完成判据与验收证据

- 遵循数据与批量任务规则第 8 条：文件落盘、数量校验、目标系统写入和读回验证全部完成才算交付
- 生图类任务必须真实看图质检，按角色形象生成规则第 9、10 条执行

删除影响：把进度误报为结果，造成文件、记录或远端写入缺失

## 10. 验证纪律

- 代码变更运行 `npm run verify`
- 文档变更做读回、链接、格式和差异检查

删除影响：可能放过代码回归或文档失真
